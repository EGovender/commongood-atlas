# Roadmap

This is a living plan, not a commitment with dates. Phases are ordered by dependency — each one assumes the previous is stable enough to build on — not by a fixed timeline. Completed milestones are summarized here; full implementation detail (design decisions, deviations, bugs found) lives in the linked docs, not duplicated in this file.

## Phase 3.8 — UX & information architecture

Adopted from an external UX review, reconciled against the actual site (not just its description): the ontology and its tooling are solid, but the site is organized around its features rather than the tasks/audiences that arrive with different questions. Confirmed concretely in the code: `/explore` and `/design`'s `<h1>`s ("Explore", "Design") don't match their nav labels ("Graph", "Model Your Program"); the graph sidebar exposes ten filter/legend sections at once with 8–9px labels and a duplicate Kind/Shapes legend; concept search has no persistent entry point outside the homepage; light-mode muted text measures 3.4:1 contrast against a 4.5:1 requirement; and there's no global `:focus-visible` treatment. ## Phase 3.9 — Programs, Results & Evidence

Adopted from an external ontology-enhancement review: the ontology modeled the grantmaking transaction end-to-end (who gave what to whom) but had no way to represent the work a grant actually funds, what that work produced or changed, or what evidence backs any claim about that change. This phase adds a second pillar — Need → Population → Project → Activity → Output → Outcome → Impact → Indicator → Target/Measurement → Evaluation → Evidence Claim → Evidence — connected to the existing one, without redesigning it. See [Relationships](03-relationships.md#programs-results-and-evidence) for the full connection diagram.

- [x] **Semantic corrections:** `Decision` redefined as the recorded determination itself (its approved/declined/conditional outcome already lived on a separate property); `Compliance Requirement` gained an explicit `appliesToAward` relationship, distinct from the Grant Agreement that specifies it; `Restricted Funding`/`Unrestricted Funding` marked deprecated in favor of `Fund.restrictionType` (backed by the `restriction-type` reference scheme) without deleting either concept or its relationships — the first use of concept-level deprecation, added as a new optional field mirroring the existing reference-data-value pattern.
- [x] **Foundation:** `Agent` added as a shared superclass of `Person` and `Organization` (no existing relationship retargeted to it — this only establishes the hierarchy for future predicates); `Project`, `Need`, `Population`, `Geographic Area` added, connected to the existing grantmaking side (`Application`/`Award --...Project-->` `Project`); `Sponsored Project` became `subClassOf Project`.
- [x] **Results model:** `Result` added as a real abstract superclass of `Output`/`Outcome` (both redefined per the spec to drop any implication that the project caused the change); `Impact`, `Input`, `Activity` added; the results chain (`usesInput`/`performsActivity`/`producesOutput`/`contributesToOutcome`/`contributesToImpact`) connects them, deliberately using "contributes to," never "causes." `Result`-as-superclass is also what let later Measurement/Evidence relationships target a single abstract concept instead of needing generator support for union-typed relationships (see below).
- [x] **Measurement:** `Indicator`, `Target`, `Measurement` added, keeping a strict planned-vs-observed distinction (a Target and a Measurement are never interchangeable); `Target`/`Measurement` value fields are plain strings, not numeric, so they can hold numeric, categorical, ordinal, or textual observations without conflating them.
- [x] **Evidence:** `Evidence`, `Evidence Claim` added, plus new Claim Type (association/contribution/attribution/causation) and Evidence Strength (anecdotal/limited/moderate/strong/inconclusive) reference-data schemes. This is the mechanism that keeps a causal interpretation of a project's relationship to a result an explicit, sourced, gradable claim rather than a plain graph fact.
- [x] **Role consolidation:** `agentPlaysRole` (`Agent --plays--> Role`) added as the preferred predicate now that `Agent` exists, superseding — but not deleting or migrating existing data off — the separate `playsRole` (Organization) and `personPlaysRole` (Person) predicates. First use of relationship-level `deprecated`/`replacedBy` fields.
- [x] **SHACL:** three new hand-authored cardinality shapes (`Target` and `Measurement` each need exactly one `Indicator`; `Evidence Claim` needs at least one `Result` and one `Evidence`) — deliberately not generalized into a rule that every relationship must be mandatory, since no other relationship in the ontology is SHACL-enforced as required.
- [x] **Worked example:** the existing direct-grant thread extended (not a sixth, unrelated engagement) with the Project an existing Award funds, the Need/Population/Geographic Area it addresses and serves, the Activity behind an already-existing Output, that Output's contribution to an already-existing Outcome and a new Impact, an Indicator/Target/Measurement (70% target vs. 64% actual), and an Evidence Claim from the existing Year 1 Evaluation (`contribution`/`moderate` — deliberately not causation).
- [x] **Explorer/UI:** a new `programs` Graph Explorer relationship-filter bucket; a new "Programs, Results & Evidence" named view; new Design Mode questions; a "Deprecated" badge (reusing the existing legal-note badge pattern) on concept cards and pages. No new category or node shape — the dataviz skill's own rule that a 9th categorical color is never a newly generated hue meant folding the new concepts into the existing `cross-cutting` and `outcomes-and-closeout` categories instead, and every new concept reuses an existing `kind` (`entity`/`process`).
- [ ] Explicitly deferred, matching the source review's own guidance: generator support for union-typed relationship domains/ranges (not needed — the `Result`/`Agent` superclass pattern covered every case that would have wanted one); migrating the six existing worked-example threads onto `agentPlaysRole`; an `Issue Area`-style dedicated reference-data browsing page (tracked separately under Phase 3.7 Milestone 5).

## Phase 3.10 — Structured Grant Terms & Candid PCS Classification

Combines two adopted delta-enhancement reviews that build on Phase 3.9 and share a worked example: replacing free-text grant restrictions/conditions with a normalized, source-text-preserving model, and adding a generic external-taxonomy classification layer proven on Candid's Philanthropy Classification System (PCS).

- [x] **Grant Term family:** `Grant Term` added as an abstract superclass (never itself instantiated) with four new concrete subtypes — `Use Restriction`, `Grant Condition`, `Approval Requirement`, `Reporting Requirement` — plus two existing concepts re-parented into the hierarchy rather than duplicated: `Compliance Requirement` and `Reporting Schedule` (`subClassOf grant-term`), and `Matching Requirement`/`Payment Condition` (`subClassOf grant-condition`, since they're the enhancement's own canonical examples of one). Every `Grant Term` preserves `originalTermText` (the verbatim source clause) alongside normalized fields, plus `normalizationStatus`/`normalizationMethod` tracking how it got there.
- [x] **New reference-data schemes:** Use Restriction Type (~20 values) and Condition Barrier Type (~15 values) — rich and Candid-alignable enough to earn real SKOS scheme treatment; everything else the family needed (`restrictionMode`, `conditionStatus`, `failureConsequence`, `approvalType`, `reportType`, and an additive expansion of `compliance-requirement.requirementType`) stayed a plain inline enum, consistent with this ontology's existing small-vocabulary convention.
- [x] **Relationships:** `Grant Agreement --specifiesGrantTerm--> Grant Term` and `Grant Term --grantTermAppliesToAward--> Award`, each declared once against the abstract `Grant Term` and satisfied by every concrete subtype via subclass substitutability (the same trick `Result`/`Agent` proved in Phase 3.9) — except `Compliance Requirement`, which keeps its own pre-existing `appliesToAward`, unmigrated. Plus `Grant Condition --hasConditionResponsibleParty--> Agent`, `Approval Requirement --requiresApprovalFrom--> Agent`, and `Reporting Requirement --fulfilledByReport--> Report` (independent of the existing `Reporting Schedule --obligatesReport--> Report`, so one Report can satisfy more than one Reporting Requirement).
- [x] **Classification Assignment:** a generic (not Candid-named) concept letting an `Award` or `Population` be classified under any external or internal taxonomy, via `awardHasClassification`/`populationHasClassification`. Splits validation into two properties — a real `reference`-typed `classificationScheme` (validated against a new `classification-scheme-registry`) and a plain-string `classificationConceptCode` (not independently validated against that scheme's actual values) — a documented, accepted limitation of the existing reference-property mechanism, which supports exactly one fixed scheme per property, not one chosen per instance. See [Data Model](05-data-model.md#known-limitation-a-reference-typed-propertys-scheme-is-fixed-not-per-instance).
- [x] **Candid PCS reference data:** two small, explicitly illustrative schemes (`version: "illustrative-subset"`, `publicationStatus: "draft"`) — Candid PCS Subjects (with real hierarchy, and `broadMatch` mappings to the existing Issue Area scheme via the pre-existing `mappings` field) and Candid PCS Populations. Three more PCS facets (Organization Types, Transaction Types, Support Strategies) are registered in `classification-scheme-registry` but deliberately left unpopulated until real data needs them. Not a reproduction of Candid's actual licensed taxonomy — there is no source file here for its real codes or full coverage.
- [x] **Generator enhancement:** optional `minValue`/`maxValue` on `datatype: "decimal"` properties, translated to `sh:minInclusive`/`sh:maxInclusive` — real SHACL validation for `allocationPercentage` (0–100), reusable by any future decimal property.
- [x] **Business rules:** four prose entries — a Grant Term should identify its Award unless still draft/unnormalized; at most one primary Classification Assignment per resource+scheme; allocation percentages should sum to 100 once allocation is asserted complete (an incomplete sum is a data-quality signal, never silently renormalized); classification rolls upward through `broader` only, never downward.
- [x] **Worked example:** the existing direct-grant Coastal Watch thread extended again with two Use Restrictions (required-use and prohibited-use), a Grant Condition ($50,000 matching funds, pending), an Approval Requirement (>10% budget reallocation), a Reporting Requirement (fulfilled by the existing Q2 Report), and three Classification Assignments (Environment as primary + Economic Development as non-primary on the Award, Economically Disadvantaged People on the existing Population).
- [x] **Explorer/UI:** the five Grant Term predicates join the existing `compliance` relationship-filter bucket; a new `classification` bucket for the two `hasClassification` predicates; a new "Grant Terms & Classification" named view; new Design Mode questions.
- [ ] **Explicitly out of scope, documented rather than built:** a live Coverage/Primary/Allocated reporting/aggregation engine — the ontology models the underlying data (explicit vs. derived classification, `isPrimary`, `allocationPercentage`) and [Relationships → Classification](03-relationships.md#classification) hand-walks the worked example's numbers under all three modes, but no computed feature exists, since the site has no financial-aggregation feature of any kind to extend; a Tides-import normalization workflow for bulk-converting existing free-text grant data into structured Grant Terms; Organization Type/Transaction Type/Support Strategies PCS facets (registered, not populated); `Award`/`Population`-only classification targets (Organization/Project/Grant Program/Funding Opportunity are valid future targets under the same mechanism, not yet wired up).

## Phase 4 — Semantic search and AI assistant

- [ ] Semantic (not just keyword) search over the ontology
- [ ] An assistant that reasons over the ontology's actual relationships (e.g., "what depends on reports?") rather than general-purpose chat

## Phase 5 — Extension beyond grantmaking

- [ ] A defined pattern for extending the core ontology into adjacent domains (fundraising, CRM, finance, programs, volunteers) as separate modules
- [ ] At least one additional domain module built out as a proof of the extension pattern

## Explicitly out of scope for now

- Building a grants-management product or any end-user application beyond the explorer
- Committing to any specific tech stack for phases 2+ before phase 0/1 are stable
- Any AI-agent code-generation capability (auto-generating APIs/schemas from the ontology) — interesting long-term, not a near-term goal
